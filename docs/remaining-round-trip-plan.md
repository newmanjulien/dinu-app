## Rules for this follow-up

- Keep [the audit](round-trip-audit.md) and this plan current as each phase proceeds. Record the chosen behavior, files changed, observed request/work effect, checks performed, and remaining uncertainty. Mark an item **changed**, **kept with reason**, or **blocked by missing evidence**; do not silently drop small items.
- Preserve server authority for permissions, claims, shared writes, booking operations, and current results. Local state may display or suppress confirmed repeat work, but cannot grant access or invent a successful server claim.
- Prefer one scoped owner for a piece of optional work and reuse a current authoritative result. Keep foreground reads ahead of speculative work. Do not combine live queries merely because they read related records: compare first usable paint, payload size, and invalidation cost.
- Do not add tests or expand the suite. Automated tests run in **Phase 6**, rather than after each implementation phase. Run the required `npm run test:perf` there for any changes to saving, scheduling, or caching. Use existing affected checks, type checks, and build only as needed. Browser acceptance remains user-led.
- A candidate with no demonstrated cost still gets an explicit decision. A source-level extra call alone is insufficient proof that removing it improves the user experience.

## Phase 2 — Remove small repeat requests

**Scope:** Fix repeated interactions where the UI already knows enough to avoid sending the same work again.

1. Suppress later `claimBuyerLinkBarShowing` calls for a member/contract pair after a confirmed successful server claim. Scope the remembered fact to the same identity and contract; an unknown claim still goes to the server, which remains authoritative. Avoid adding per-member claim reads to every ordinary contract metadata subscription just to save this rare mutation.
2. Keep recent buyer activity rows visible across a quick panel close/reopen and refresh only when stale or explicitly requested. Retain the existing freshness behavior while the panel stays open; compare reopening request counts.
3. Coalesce rapid support-widget expand/dismiss changes to the final desired preference and flush on scope exit. Apply the same local-first, final-value approach to Help checkbox saves if the current pending/disabled interaction can be improved without losing a change. Preserve cross-device updates and explicit retry on failure.
4. Reuse a bounded, scoped **settled exact-term** Home result when a term is revisited; invalidate it on relevant writes and scope changes. Evaluate the same pattern for HubSpot deal search, keyed by connection and term with a short freshness limit. Do not treat provisional local filtering as a complete server search result.

**Exit:** Every listed surface has either fewer repeat requests by construction or a recorded reason that a change would add more work or degrade correctness. The bar claim is the default implementation target even if sampling is sparse.
