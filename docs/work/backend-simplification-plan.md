# Backend simplification plan

This plan covers the six accepted review items (2–7): bounded operation retention, coherent change heads, buyer-link vocabulary, canonical approval policy, explicit item audiences and retirement of completed backend systems. It contains seven ordered packages and 28 steps.

The original delivery of this plan was planning only. The user later authorized implementation; its local checks passed, but the user's subsequent Convex push rejected the review-group field required by the original D3 design. The bounded correction addendum below supersedes that design and records the five newly authorized corrections. It does not reopen the completed original packages or certify deployment. The user explicitly deferred the concluding audit and instructed us to stop after these corrections and their independent validation.

The proposed defaults are seven days of retry validity and 90 days of full settled output evidence. The user accepted bounded retention; these exact durations are design assumptions, not user-supplied requirements. Actual target schema, data, queued jobs and provider obligations remain uninspected release prerequisites.

## Scope and preserved behavior

Use `playbook | buyer-link` consistently for change kinds and approval contexts. Preserve immutable captured templates and independent item/version identities; pending versus applied wording; compact projections; independent document, state, content, authoring and structure revision clocks; two independent review groups; and real authorization and freshness checks.

HubSpot's current control over contract creation, naming, buyer sourcing, work admission, deal associations and integration policy stays unchanged. Its callers may change operation envelopes and storage references required by this plan. Preserve business rules, scopes, original actor/destination facts, installation and generation fences, canonical deduplication and external-outcome ambiguity handling. Preserve CSM's separate operation protocol, booking/meeting preparation split and compatibility for issued links.

Follow `AGENTS.md` and read `src/convex/_generated/ai/guidelines.md` before Convex work. Preserve all unrelated staged, unstaged and untracked work; this workspace already contains substantial edits in affected UI, authoring, account and cache paths. Use inline Tailwind and existing styling for any necessary UI changes. Do not create or expand tests. Maintain affected existing fixtures and assertions without weakening their guarantees. Browser or Playwright work is unnecessary here.

The final application has one canonical schema/client, without permanent dual formats or a general migration framework. Temporary preservation tools are release artifacts. This plan authorizes no live reads, mutations, deployment or destructive reset; a future release must explicitly authorize its target and actions.

## Shared implementation contracts

### D1 — Immutable expiry, enforced before replay

Use `op1:<createdAtMs>:<randomUUID>` for contract operations and every independently replayable Playbook command. Create it once per user intent, persist the original identity and exact input bytes, and reuse both unchanged. The timestamp is an untrusted identity component, not authorization or a business event timestamp.

Derive `retryUntil = createdAtMs + 7 days`. At mutation admission validate the protocol, full format, safe integer timestamp and `createdAtMs <= serverNow + 60 seconds`; reject at `serverNow >= retryUntil` before replay, no-op returns or new work. Retain company/actor/contract authorization and exact-input collision checks. The exact expired identity must fail even after its receipt is physically gone. A changed timestamp is a different identity and must never be minted automatically to retry uncertain work. A future-clock rejection has a distinct pre-admission error; a corrected identity is allowed only after the server established that the rejected request made zero business writes.

Validate every command as well as the outer batch. Cover create/relink, buyer-link creation, saves and their command receipts, decisions, proposal support/withdrawal, approval requests/completion, authenticated/anonymous discussions, export reservation and quote reservation/commit. Leave unrelated browser/event IDs, CSM identities, template revision identities and template item-creation receipts alone unless a concrete dependency requires a change.

Keep the parser/key builder pure for queries and internal verification. Mutation admission reads server time. Result queries remain read-only, return the immutable deadline and cannot restart work; never add query wall-clock reads. Clients stop automatic reattachment/resubmission at expiry, but server admission is authoritative. Preserve expired unsent intent as blocked recovery for review against fresh state; only a deliberate user action after that review creates new identities.

Internal continuations also enforce the original deadline before adopting new business state. Expired core preparation seals an explicit expired outcome and disposes of private work. Dispatched/uncertain external work remains under its existing provider/delivery owner for reconciliation; operation expiry must not infer failure or trigger a fresh dispatch.

Receipts store `retryUntil` and indexed `gcAfter = retryUntil + 24 hours`. The grace delays physical cleanup, without extending validity. Delete a due receipt only after output ownership transfer, native promotion and private cleanup are complete. Ordinary discussion receipts use the same admission/physical-retention policy while messages and meaningful tombstones remain. Held receipts are rediscovered through durable bounded maintenance, without an unbounded scan or immediate retry loop.

### D2 — Separate replay, output evidence, native ownership and document lifetime

**Output ownership.** Introduce `contractOutputs` and `contractOutputChunks`, owned by the existing reservation/proof modules. Move output preparation, generation, verification, cleanup, immutable manifest and proof chunks out of `operationReceipts`/`operationReceiptChunks`. Each output owns its company/contract identity. Receipts replay bounded results referring to that output; Word attempts and quote pushes use `outputId`. Native preparation remains transient receipt-owned work. Do not duplicate complete proof or result JSON.

Retain immutable captured source/actor/destination facts, owner bindings, seals, four-chunk proof folds, hash/order/count/byte verification and fresh final release checks. A reused canonical quote push retains its original output owner. Historical metadata reads are separate from live release admission: compact history cannot regenerate or release bytes.

**Native promotion.** A result seal may name an ordinary document or a document staged by another receipt. Membership in receipt B's `nativeResult` does not grant B ownership of receipt A's stage. Before deleting a complete receipt, process only surviving rows in `contractDocuments`, `contractChanges` and `contractChangeDecisions` whose `stage.receiptId` equals that receipt, using the existing `by_stage_receiptId_generation_unit_slot` indexes. For each surviving row in the adopted generation, require matching company/contract, complete owner, sealed stage, exact generation and membership in the corresponding `nativeResult` field/list before clearing `stage`. Preserve every payload, ID, hash, source/predecessor relation, actor, timestamp and revision.

Run bounded first-range batches as promoted rows leave their stage index; this needs no permanent adoption ledger. Missing IDs from a historical seal and previously promoted rows are harmless: contract/source cleanup can already have removed them. Borrowed documents remain under their actual owner's promotion. A surviving staged row with a missing/mismatched seal fails closed. Drain obsolete/unadopted generations under native garbage ownership, without publishing them. Retain the owner/seal until promotion, obsolete-generation cleanup and receipt-section disposal finish; fence stale callbacks from appending or re-adopting. Update `nativeStage` and `outputProof.committedDecision` together. Private native documents use freshly owned chunks today; retain that isolation so their garbage path can safely drain private bytes.

**Retention policy.**

| Owner | Retention and end condition |
| --- | --- |
| Exact operation input/result and private preparation | Seven-day validity; physical disposal after 24-hour grace and dependency cleanup |
| Unreleased/abandoned output with no external effects | Dispose after operation expiry and private proof/native cleanup |
| Word/provider file bytes | Existing one-hour local eligibility, 15-minute read grace and provider payload rules; preserve independent attachment holds, currently up to 30 days after acknowledgement |
| Released/acknowledged output or terminal provider output: full manifest/proof | 90 days from immutable settlement, and until every independent file, delivery, lease and reconciliation hold ends |
| Compact historical output fact | Company lifetime; output kind and IDs, title, actor profile/membership IDs, original request/release/acknowledgement times, file name/hash/size, document/source/proof fingerprints, provider destination/remote identity and factual disposition |
| Dispatched/unknown/verifying/attention provider work, unresolved email outcome or live lease | Existing outcome/canonical fence and all evidence required for safe reconciliation, without a fixed TTL |
| Successful canonical provider fence | Company lifetime; evidence expiry must never allow an identical successful create to dispatch again |

Set `settledAt` once from a conclusive lifecycle transition after related execution leases end. Reads, retries, `updatedAt` and client acknowledgement times cannot slide that deadline. An acknowledgement or independently active delivery can impose a hold without rewriting settlement. Pending/uncertain outcomes have no settled TTL. Missing responses, file expiry and contract deletion are never negative provider evidence.

After full-evidence compaction, the product certifies historical identity and observed outcome, rather than reconstructing every original wording and approval detail. Delete proof fragments, arbitrary command/result JSON, actor email snapshots and execution tokens when no reconciliation hold requires them. Indefinite full reconstruction is deliberately outside this proposed policy.

**Operational rows become non-owning.** At full-evidence compaction, convert each terminal Word attempt in place to a compact variant retaining its physical acknowledgement identity, company/contract/output identity and factual release/acknowledgement fields. Clear exact `inputs`, execution `claim`, `fileId`, direct `documentId`, receipt references and obsolete request-key data after their consumers have finished. Before compaction require acknowledgement closure, lease completion, completed byte deletion and no delivery/attachment/reconciliation owner still needing the full row. Resolve or compact terminal delivery references in the same lifecycle; never delete an attempt still needed by an unresolved activity/upload outcome. Compact attempts are historical metadata, not document holds or executable work.

Likewise, terminal quote pushes become compact provider/observation variants retaining company/contract/output identity, destination, canonical key, fingerprint/payload hash, remote quote ID/link and factual state/message. Remove document/receipt references, payload/file references, jobs, claims, leases and detailed failure/recovery bytes once their holds end. Retain successful canonical fences and all compact terminal summaries for company lifetime; unknown or otherwise unresolved work remains full until reconciled. Keep `by_canonicalKey_and_state`, contract/company lookup and `by_outputId` where used; remove attempt/push `by_documentId` and `by_reservationReceiptId` indexes when callers move. A compact `outputId` reference is never a full-document hold.

**Latest quote observation has its own owner.** Add optional constant-size `quoteRequests` metadata to the contract root: `{ watermark, latest?: { requestedAt, pushId } }`. On each new reservation atomically allocate `requestedAt = max(serverNow, watermark + 1)` and advance the watermark. Commit atomically updates `latest` only when that reservation's `requestedAt` is newer, including when the request reuses an older canonical push. Exact replay does not allocate another request. This preserves request ordering when preparations finish out of order; push creation/settlement time is irrelevant. No document/state revision or directory timestamp changes solely for this metadata. `hubspotQuotes.latest` reads the root pointer and the push's full/compact summary with existing membership, company and contract checks. The pointer/watermark disappear with the contract; company deletion erases the push/fact under existing provider rules. Before deleting old receipts, conversion derives the watermark from the greatest existing reservation/commit requested time and the latest pointer from the latest valid commit receipt. Reuse neither changes the push's output owner nor creates another remote quote.

**Shared documents have a contract-level reclamation boundary.** Ordinary manifests share unchanged chunk IDs, and current storage has no reverse chunk references. Keep adopted document manifests/chunks for the live contract's lifetime, as the existing ordinary writer already does. After contract deletion retain the contract's remaining document set while any full-output evidence or unresolved-effect owner requires document bytes. One held output can therefore retain other historical chunks from that contract; an unresolved outcome can extend that coarse hold indefinitely. Compact facts, compact attempts and compact pushes do not impose it. There is no promise of per-document or 90-day chunk reclamation for live contracts.

Reuse the durable `contractCleanups` marker for a document-hold waiting phase after source cleanup. Before source deletion, verify full output proof and document seals/chunks in bounded folds. Once core preparations are retired/fenced, no new output/document hold may be acquired for a deleted contract. All hold acquisition/release and the transition into document drain consult the same marker transactionally; existing unresolved owners may settle/release their hold but cannot reopen the drain. A hold release wakes this marker; indexed scheduled recovery handles a lost wakeup without hot-spinning on indefinite holds. When the last full/effect hold ends, drain all remaining manifests and chunks by contract in bounded resumable batches, then remove the marker. No chunk is deleted individually merely because one output expired. Remove sticky `retainedAfterDeletion` marking and its index/reserves after conversion handles existing markers; preserve document integrity/capacity accounting for the new physical shape. Company deletion still erases its full owned set through the shared budget and provider-erasure rules.

Document and output cleanup thus remain separate: an output may compact at its own deadline while shared bytes wait for another legitimate hold. Two manifests sharing a chunk stay readable while either legitimate owner exists, and a deleted contract's remaining bytes are eventually reclaimed after its final hold without waiting for company deletion. Private unadopted native garbage remains the exclusive-owner exception described above. This design adds no chunk reference writes to hot saves.

**Late download acknowledgement.** Accept truthful acknowledgement after file expiry only within seven days of the server-recorded first `releasedAt`. `initiatedAt` cannot extend that deadline. Preserve the first accepted acknowledgement and independent delivery hold. After acknowledgement closure the journal removes its terminal entry without regenerating files or provider activity. The 90-day evidence owner covers this acknowledgement window.

### D3 — Coherent heads and independent reviews

Export one shared `playbook | buyer-link` validator/type and use it directly for approval contexts; remove `contextForChange`. Rename stored/runtime `buyer-proposal` change variants to `buyer-link`. Keep meaningful discussion/proposal concepts and user-facing proposal wording.

Store heads as a kind-discriminated union, with company/contract/key and required nullable `current`/`applied` bundles. A Playbook bundle owns its change ID, option ID and policy. Policy `none` carries no decision; required-policy current state has `review: {kind:'pending', admissionRevision} | {kind:'decided', decisionId}`. Required-policy applied state requires its exact approved decision ID. Buyer-link current state has a change ID and the same pending/decided review bundle; applied state requires change/approval decision IDs. No buyer-link variant admits Playbook projection fields. `activePlaybook` exists only on the Playbook head and remains the atomically maintained indexed projection of current/applied non-base options. Delete heads with neither current nor applied state.

This places the pending admission revision inside its activation; restoration/withdrawal cannot leave an unrelated revision behind. Shared variant constructors/projection helpers serve ordinary and native/staged writers. Continue cross-record company/contract/kind/key, exact decision relation, stage reachability, source revision, support aggregate membership, current/applied equality and freshness checks. Decision status remains derived from its authoritative record. Preserve stale buyer support's effective fallback to applied state and undo of applied wording after its original thread is deleted.

Root state uses fixed, legal Convex fields `reviews.playbook` and `reviews.buyerLink`, each `{ identity, completion? }`; each completion retains its captured `reviewIdentity` binding and existing outcome payload. Canonical change/context **values** remain `playbook | buyer-link`. One shared typed `reviewGroupKey(context)` maps these values to `playbook | buyerLink` for computed structural reads/writes; this mapping is required and is not a second domain vocabulary or a compatibility adapter. Use it in ordinary/native/email consumers and the preservation converter's bundled helpers. Do not index the structural object directly by an unconverted context or rename canonical string values. Keep exactly two independently fresh groups. Playbook counters remain root counters; buyer-link counters remain `DiscussionIndex.supportSummary`. Preserve constant-size exact readiness counts, bounded indexed selected-Playbook reads, paged details and native cursor/split metadata. Keep admin choices, buyer-link token/currentView checks, notification coverage and request cutoffs distinct. Only approved wording changes document revision; only a group's semantic review set changes its identity. A representational correction alone changes no review identity, completion, business clock or immutable proof bytes.

### D4 — One policy and explicit audiences

Drafts store canonical `instructions` and `approvalPolicy`. Remove `AuthoringInstructions`, `changesNeedApproval`, pseudo-key derivation and precedence rules. Keep the approval-guidance text box's label, position and permissions. It reads/writes policy directly: nonblank text yields `{kind:'required', instructions: exactText}`; clearing or whitespace-only text yields `{kind:'none'}`. Preserve other instruction fields' empty-versus-absent semantics and exact nonblank guidance. Dirty checks, remote/confirmed adoption, recovery, normalization and read-only display all use the same policy. Render policy separately from the four ordinary instruction definitions.

Require explicit `audience:'rep'` or `audience:'buyer'` on both template variants, transported structures and decoded `ItemStructure`. Branch on the literal throughout. Rep keeps instructions/policy/concessions; buyer keeps explanation-only content, text triggers and its existing editing restrictions. Packed structure tags already distinguish rep (1) and buyer (2); retain those bytes and return explicit literals from the decoder, without a gratuitous codec version change.

Preserve compact heads versus sole revision-body ownership, captured template/version/item identities and independent clocks. Fix property-presence guards, especially `playbookItemRevisions.businessItem`, before adding the rep field. Seeds/imports emit canonical audience/policy; historical import adapters may translate known old input once. Recount/recertify representational changes from the original frozen data, without recapturing current authoring or inventing business revisions.
