# Backward compatibility audit

> Historical implementation/review snapshot. Recorded results describe that stage only.
> Contract conversion, tuple-chunk and compatibility instructions below are superseded by
> the [current contract release procedure](../deployment.md#backend-ownership-conversion).
> Read the current architecture in [data model](../data-model.md); no live cutover is certified here.


## Scope and result

Removed `src/routes/(workspace)/admin/+page.ts`. It existed solely to preserve saved links to the former template editor and issued a permanent redirect to `/template`, preserving the query string. `/admin` no longer has a route definition.

The remaining findings below are an inventory, not implemented removals. Inspected application routes, client code, Convex functions/validators/schema, scripts, and relevant rollout documentation. Followed references beyond keyword matches to distinguish current callers, unused adapters, old storage admission, and operator-only conversion tools. Preserved pre-existing workspace changes. No backend deployment or database mutation was performed.

This repository contains substantial compatibility scaffolding. It is not confined to the old route or files named `legacy`.

## Removal order for a single current contract

1. Remove unused old public API wrappers, their exports, old query projections and `legacyViews`. Update generated API declarations through the normal code generation workflow.
2. Update current callers of old routes (especially download acknowledgement), then remove those aliases. Remove old buyer routes, token admission, cookie adoption and Word namespace if the intended policy rejects all historical input.
3. Choose the current storage format for each table; remove old union members, fallback reads, old fields, dual-range indexes and lazy conversions together. Remove retired tables and their cleanup phases/drains. Keep canonical tables merely carrying old names separate from truly retired storage.
4. Simplify booking protocols, metadata, receipt formats and draft checkpoints as complete producer/consumer changes. Both areas still contain current code depending on the old branches.
5. Remove historical migration entry points, maintenance detection, scheduler stubs, transition scripts and stale rollout instructions after choosing whether offline historical seed import remains supported.

No live data operation is necessary to review or implement those source changes. Applying a stricter schema to populated deployed data is a separate operation; current deployment contents and scheduled work were not inspected here.
