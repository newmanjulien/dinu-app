# Buyer naming cutover

> Historical implementation/review snapshot. Recorded results describe that stage only.
> Contract conversion, tuple-chunk and compatibility instructions below are superseded by
> the [current contract release procedure](../deployment.md#backend-ownership-conversion).
> Read the current architecture in [data model](../data-model.md); no live cutover is certified here.


The final application requires canonical `title` plus explicit manual/HubSpot `buyer` source. Normal saves are command-only, receipt storage is canonical-only, and refresh bookkeeping has its own coordinator. Old contract endpoints, title aliases, embedded-state/destination fallbacks and retired receipt owners are absent. This requires coordinated backend/client/data cutover. The local implementation has not deployed or converted a database.

## Prepare two source states

Retain the final source as the release candidate. In a separate temporary maintenance checkout, copy `scripts/migrations/buyerNaming.ts` to `src/convex/buyerNamingMigration.ts` and `scripts/migrations/buyerNamingTransitionSchema.ts` to `src/convex/buyerNamingTransitionSchema.ts`. Imports resolve from either location. Add the exported `buyerNamingTransitionTables` to the schema table object and set `schemaValidation: false`. Keep all final tables/indexes, including `contractBuyerRefreshes`, and add only the temporary tables. The empty `terminologyMigrationState` definition activates the existing traffic gate; migration functions also require disabled validation. Do not add these files/tables to the final deployed runtime.

The temporary receipt tables retain their old company/key and receipt/order indexes. Validation is disabled only during stopped traffic so the bounded converter can read original records and write checked final values; this is not a mixed-client compatibility release. Compile both prepared states locally. Stage/backfill indexes before use when necessary; confirm the canonical association ownership index, coordinator contract/company indexes and directory `search_title` are ready.

## Operator sequence

1. Identify and announce the exact deployment under `convex-deploy-guard`. Obtain its required explicit production consent before production snapshots, environment changes, deployment or migration. Rehearse the complete sequence on a snapshot-seeded preview first. Take and verify a coherent rollback snapshot and retain the matching old backend/client.
2. Inventory unsaved browser journals separately as described below. A server snapshot cannot capture another tab's unsaved edits. Enter maintenance and deploy the prepared transition backend through the applicable guard. Stop provider, refresh, cleanup and cron admission and drain/cancel already queued and in-flight work, including old refresh attempts. Provider flags alone do not stop every worker. Do not convert while an old writer or cleanup continuation can still change these records.
3. Run `buyerNamingMigration:consolidateReceipts` with `{cursor: null}`, passing each returned cursor until `isDone`. Each transaction validates one old receipt and at most 63 ordered, correctly owned chunks, compares any canonical duplicate's company/key/exact raw inputs/results, writes a missing canonical receipt, then deletes the old receipt/chunks atomically. A conflicting duplicate or malformed envelope refuses the batch without deleting source data. Record deployment, snapshot, cursors, counts and exact payload comparisons outside the deployment.
4. After receipt consolidation, run `buyerNamingMigration:pruneOrphanReceiptChunks` to completion using its cursor. It deletes only chunks with a valid old receipt ID whose parent is absent; a surviving parent or malformed identity refuses the batch for investigation. Record the orphan inventory/removal proof. Require `buyerNamingMigration:receiptRetirementStatus` to return both `legacyReceiptsRemain: false` and `legacyChunksRemain: false`. Do not proceed on an incomplete proof or delete an owner to bypass a conflict.
5. Run `buyerNamingMigration:convert` with `{table, cursor: null}`, then returned cursors until `isDone`. Finish tables in order: `savedContracts`, `approvalRequests`, `emailDeliveries`, `operationReceipts`, `contractDirectory`, `contractAccess`, `contractHubspotAssociations`. Every transaction visits one native row with bounded reads; retain cursors for interrupted resume. Root conversion preserves existing canonical buyer evidence, exact titles and native IDs; it does not republish or call HubSpot. Approval receipt inputs remain `[contractId, expectedEditRevision]`; only the explicitly scoped result title shape changes, using the shared chunk validator/encoder.
6. The association pass moves applicable old `buyerRefresh` metadata to the uniquely owned, destination-bound `contractBuyerRefreshes` row. It preserves relevant freshness/suppression, sets the lease to zero and creates a new attempt identity so no old worker can commit. Inapplicable installation/source metadata grants no new authority. Invalid metadata, ownership or an unexpected existing coordinator refuses the batch. The same transaction removes the embedded metadata; a retry after commit sees no old field. No dual-read fallback is installed.
7. Verify every root's unique working child, owned destination and exclusive company/connection/deal ownership; validate all final records and both directions of directory fidelity. Require obsolete title/access fields and embedded refresh metadata absent, retired receipt stores empty, and every coordinator bound to its live contract/association/destination. Compare exact original versus converted title strings, content/review/publication clocks, approval/email captures, operation keys/raw inputs/raw results (apart from the explicit approval-result rename), chunk payloads and export provenance. Exercise interruption/resume, duplicate/conflict refusal and coherent rollback in preview. Record index readiness and these proofs before final removal.
8. Remove the two temporary modules and all `buyerNamingTransitionTables`, restore strict schema validation, then deploy the final backend/client together. Final schema contains neither retired receipt table, `contractAccess` nor the maintenance marker; final `operationReceipts` exports no consolidation/status endpoint. Require old tabs to reload; removed endpoints and old title/snapshot-save payloads are refused. Resume workers and exit maintenance only after final validation. Retain snapshot/evidence until acceptance. If conversion fails, keep maintenance and the source tooling/data intact; rollback restores the matching backend/client/snapshot rather than an old client alone.

## Browser journal recovery

Confirmed IndexedDB **DB13** is disposable and evicted/reacquired. Session-storage journals remain separate under their existing deployment/user/membership/contract namespace. Normal readers/writers accept **v7 only** and never accept old title aliases or commandless saves.

The per-journal boundary attempts supported v4/v5/v6 conversion only when that exact journal is read. It validates the full source, immutable request, command identities and request/queue/latest-intent relationship before one durable replacement. Supplied queues must retain the submitted batch exactly and preserve newer intent after acknowledgment; a bounded overflow retains its complete target. Newly inferred, genuinely unsubmitted commands have IDs persisted before replay. There is no namespace marker or whole-namespace exception gate. Unsupported/invalid/ambiguous records and failed storage replacements retain their original serialized bytes; refusal blocks only that contract through the existing recovery error and write guard.

A historical submitted **commandless snapshot request is refused unchanged**. Do not attach invented commands to its existing operation ID, fabricate acknowledgment from choice equality, silently discard it, or restore a permanent snapshot-save API. Before enabling recovery for such a record, preserve/export its raw journal and identify the exact deployment/user/membership/contract, immutable operation ID, revision, payload and any real command/application identities. In the bounded maintenance/recovery phase resolve that original operation with exact canonical/retired receipt and ordered live evidence. A last-operation marker must be the genuine original identity; later unrelated state or absence of a receipt alone does not prove whether a request committed.

If its exact result is established, preserve that result and infer only truly unsubmitted residual work. With no real newer command tail, derive the residual transition from the original request's choices to the latest local intent, then apply it over the resolved result; preserve genuine tail/application identities and order when present. For the audited empty-base/empty-queue/request-selects-A/latest-empty case, the later removal of A must survive both transport and live-last-operation acknowledgment. Construct a checked current journal, persist it before replay, and retain a checkpoint until all remaining work resolves. If evidence cannot establish correspondence without replacing real identities, keep the original bytes and that contract's refusal pending explicit bounded recovery. This release gate has not been exercised against real historical journals/receipts; a passing current fixture is insufficient.

## Preserved data and source ambiguity

Preserve root IDs, exact title strings, children, comment text/ownership, auth/author keys, command/request/application identities, saved/review/publication clocks and historical captured titles/destinations. Roots with no destination become manual; roots with a retained destination become unresolved HubSpot buyers unless they already have canonical evidence. A deal title is never verified company evidence. Retained links cannot prove whether an earlier manual rename happened after uninstall; ambiguous records remain “Buyer” until a valid refresh, an actual changed manual rename or accepted relink establishes the source. There is no bulk provider lookup or message-row rewrite.

These do not prove historical request resolution, real storage/quotas, populated cutover, native cursor resume/rollback/final deploy, provider consent/races or measured reactive-query savings.
