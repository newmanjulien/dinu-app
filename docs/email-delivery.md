# Email delivery

The repository owns three Loops transactional templates. [templates.json](../emails/templates.json) contains their stable names, subjects and completed-review CC setting. [invitation.lmx](../emails/invitation.lmx), [approval.lmx](../emails/approval.lmx) and [decision.lmx](../emails/decision.lmx) contain their actual copy and paragraph structure. They use native `{data.*}` variables and explicit `<Br />` line breaks. Loops compiles these files; the app does not render HTML or pass an assembled body through a wrapper.

The user approved short contract notifications with summary counts and a contract link. Approval mail reports pending, previously reviewed and non-required counts; completed-review mail reports approved and not-approved counts. Zero counts are shown. Concession descriptions and individual reviewer labels are omitted from email; users open the saved contract for the concession details. On 2026-10-28 the user narrowed completed-review CC to the reviewer whose action triggered that notification. Subjects, notification triggers, link destinations, invitation copy and delivery/retry workflows retain their existing behavior.

[emailNotifications.ts](../src/convex/emailNotifications.ts) prepares a typed notification containing its kind and scalar data: names, URLs and counts. Counts come from captured review statuses, so sending needs no concession-description queries. Delivery snapshots remain necessary for approval coverage and frozen counts. The decision event captures the triggering reviewer ID atomically with that decision; snapshots contain no reviewer IDs, and claims read no snapshot or attribution rows for CC. Immutable decision receipts retain historical reviewer identity. Cleanup C3B removes current attribution storage and reconciliation entirely; current reviews keep only concession, lifecycle and status.

[emailSender.ts](../src/convex/emailSender.ts) coordinates preparation, native provider quota, a fresh guarded claim, one external request and outcome persistence. [loopsEmail.ts](../src/convex/loopsEmail.ts) owns provider configuration, template selection, HTTP requests and safe response classification. Only completed-review sends include the `cc` variable. Each notification checks its own configured template ID, so an absent approval ID does not block invitations.

## Template publishing

Prerequisites: the verified `juliennewman.com` sending domain, a server-side API key with Content API access, and team CC/BCC support. The user confirmed enabling CC/BCC fields on 2026-10-28. Loops' default one-address CC limit is sufficient for the approved triggering-reviewer policy; no support request to increase the limit is needed.

Only completed-review mail uses CC: the primary recipient is the live contract creator, with the triggering reviewer's current company-member address in CC. That ID belongs to the queued event, so a retry retains the same reviewer. If the reviewer is the creator, shares the primary mailbox, has an invalid address or is no longer a live company member, CC is empty. Invitation and approval-request mail omit CC/BCC entirely; no notification uses BCC. The decision template uses Loops' Content API data-variable spelling, `{data.cc}`, in its CC field. This avoids requesting Loops' feature-gated CC/BCC settings on templates that do not need them.

Choose the sender mailbox; the domain alone is not a complete sending address. Securely supply `LOOPS_API_KEY` and `LOOPS_SENDER_LOCAL_PART` in the operator environment. The latter is only the part before `@`; Loops supplies the team's verified domain. The display name stays `Dinu`. Secrets never belong in chat, committed files or frontend variables.

- `npm run email:setup -- --help` describes the command.
- `npm run email:setup -- --check-source` parses local XML and reports variable names. It requires no credentials and makes no account requests. XML validity does not certify Loops compilation or client rendering.
- `npm run email:setup -- --diagnose` follows the normal setup path but, after a provider rejection, reports only a safely classified configuration area. It does not print provider response bodies, email addresses or credentials.
- `npm run email:setup` discovers templates by their exact stable repo names and creates missing ones. It prepares all changed drafts with revision-protected updates, reads back and validates every changed draft, then publishes and verifies each result. Transactional updates include only data-variable fallbacks; contact- and event-property fallbacks do not apply. Already matching publications are left alone. Compiler warnings, mismatched source/configuration or changed draft identities/revisions stop publication.
- `npm run email:setup -- --check` reads published configuration without making changes. It compares parsed XML, allowing indentation/self-closing-tag spelling differences and Loops' normal whitespace collapsing while preserving block structure and text. Equivalent editor/LMX header variable spelling is accepted. These templates leave document styling unspecified, so Loops' returned default top-level `<Style />` is not treated as a content change; an explicit repository `<Style />` is compared exactly.

Repository-owned configuration includes LMX copy/structure, subject, sender, reply-to, format, preview text and the decision template's CC setting. The app always supplies the decision's `cc` data variable, so it has no fallback value. Fallback maps merge per key in Loops: the command reads existing values and deletes obsolete keys explicitly with `null`. This prevents an old empty CC fallback from being validated as an address or surviving an update. Parsed XML comparison preserves block structure and code-block whitespace while accepting Loops' normal text-whitespace collapsing, indentation between blocks and equivalent self-closing tags/header variable spelling. As the repository omits an optional top-level `<Style />`, Loops' provider-owned default style is accepted; adding one to a repository template makes its exact attributes source-controlled.

Both account modes print `LOOPS_INVITATION_ID`, `LOOPS_APPROVAL_ID` and `LOOPS_DECISION_ID` for subsequent backend configuration. Explicit operator ID overrides are optional; they must refer to the corresponding stable template name and ID. Duplicate names require an explicit ID rather than an arbitrary selection. A partial successful run rediscovers its created templates on the next run. An ambiguous creation is never retried automatically; inspect the account before another creation attempt. Do not rename the managed templates in Loops.

Run one publisher at a time and avoid editing these templates in the dashboard during setup. The publish API has no revision precondition or atomic multi-template transaction. The command checks the draft identity/revision again immediately before each publication, but that check cannot lock the provider draft. A later failure can leave mixed publications; diagnostics report which publications were attempted and verified. No request is retried automatically. Inspect an uncertain result, then use `--check` or rerun setup before activation; a draft-validation failure before publishing leaves all live versions untouched.

The commands resolve source paths relative to the script, independently of the working directory. They never send email, modify Convex deployments or create audience contacts. Content API calls have a separate 60-per-minute baseline; publishing belongs in operator tooling, not delivery actions. Published configuration checks are separate from rendering and delivery acceptance.

## Outcomes and recovery

Approval requests capture selected concessions and statuses against the contract's immutable template. Completed-review events capture the triggering reviewer during the decision transaction and review statuses during preparation while their generation remains eligible. Claims resolve current recipient eligibility: approval mail goes to the configured request recipient; decision mail goes to the live contract creator with at most the triggering reviewer in CC, excluding the primary mailbox. Invitation plaintext tokens exist only in the inline action and outgoing message; the database stores their hash.

Loops returns `{ success: true }` after accepting the send request. It does not return a message ID or separate primary/CC acceptance results. Stored `sent` means provider acceptance, not inbox delivery. Explicit request rejections are failed; HTTP 429 is retryable. HTTP 409, server errors, unexpected success bodies and network/timeout failures after dispatch are uncertain. Idempotency keys include deployment, delivery ID and attempt; a duplicate-key conflict is never interpreted as proof of successful delivery.

Uncertain outcomes never authorize automatic resend. Approvals expose the existing ten-minute cooldown and explicit retry warning; decision retries remain limited to three provably failed attempts. Invitations retain five inline workers, ordered results, a four-minute deadline and explicit resend. Only result persistence retries inside a sending worker. Recovery consults native scheduled job state and preserves the inline action's recovery grace. Logs contain delivery/attempt IDs, stages and safe status diagnostics, without provider bodies, content, addresses, tokens or credentials.

The native rate limiter reserves this deployment's provider work at eight per second with capacity one and a one-minute waiting budget before claims. This gives headroom below Loops' ten-per-second team baseline; reservations do not guarantee the exact spacing of subsequent HTTP dispatches. Other deployments/tools can consume the shared team quota, and provider 429 handling remains necessary. No separate application queue is introduced.

Replaced deliveries cancel old native jobs and drain snapshots under the shared transaction budget. Retired deliveries retain a complete disposal marker and are ineligible for prepare/claim/complete/retry/recovery. Continuations carry the generation; an indexed quarter-hour resumer discovers failed jobs independently of Clerk credentials. Company/contract cleanup shares nested snapshot budgets and cancels disposal jobs before deleting the parent. No snapshot body is needed merely to discover disposal work.
