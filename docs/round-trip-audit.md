# Interaction round-trip audit

Updated: 2026-11-26. Source review and local verification are complete; the production release is held by independent preservation gates. No user-flow runtime trace or production latency sample was collected. This audit concerns requests started by ordinary UI use, including SvelteKit proxy routes that call Convex. A client subscription is a live server read, but its registration and reevaluation should not be counted as one HTTP round trip per event.

## Objective and status

Find interactions that can update immediately from local state and send less work to Convex, while preserving authoritative shared writes, permissions, and cross-device state. The findings table describes source behavior found before implementation began; it is not a measured backend execution count or latency comparison. Current implementation progress is recorded under the plan.

### Expected effect

- **Visible waiting:** At audit time, saved-contract navigation awaited a server-side title read; Phase 5 removed that wait from client data navigation. Phase 8 overlaps the buyer document's initial state and template reads when the page-context version is still current. Phase 10 combines the normal buyer Word-download snapshot into one Convex read before generation; an oversized result retains the serial fallback. Eligible saved documents have a separate link-status read that starts alongside metadata; the activity panel previously reread on reopen; and Phase 28 removes the cold rename path’s extra read-before-write wait. A booking zone change can clear visible slots while another provider read runs. Discussion reply fanout and template content fanout may compete with first usable document/editor views; their effects need timing data. Phase 14 adds provisional local Home filtering; HubSpot search caching could improve repeated searches.
- **Request and provider volume:** Contract choice saves, remaining Home search terms and startup reads, speculative buyer-link browse, foreground checks, buyer-name refreshes, clause telemetry, automatic HubSpot prefetch, booking zone changes, seller avatar reads, hover and onboarding warms, one-time claims, and setup booking's possible attempt rebind can be reduced. Short Team revisits also recreate query owners, though client cache reuse may avoid fresh backend work. Access-document writes and active-link history scans can increase backend query work without adding an explicit client request. Many paths run after a local update or in the background, so fewer calls do not automatically mean a faster click.
- **Necessary authority:** Contract creation/publication, approval decisions, deal linking, export/push preflight, permission checks, and discussion writes need server confirmation. Local UI should display draft state immediately while those operations remain authoritative.

## Broader causes and other affected screens

The findings are not isolated button handlers. Four shared design choices account for much of the repeated work. The source confirms the call paths and data dependencies; it does not establish that every eligible live query actually reruns or sends a new network response.

1. **Access and presentation share high-fanout documents.** `requireMembership` reads the profile, membership, company, and deletion marker for authorization. Home lists and setup hints, Team pagers, saved-contract state, template reads, HubSpot status, and setup booking all use this access path. Small UI writes to those documents can therefore affect views far beyond the control that was clicked. The strongest example is the support-widget collapsed flag on `memberships`: it is useful to the viewer query, while unrelated Home and document queries also read that membership for access. Help preferences on `profiles` have the same shape; Home contract cards and Team rows also hydrate other people's full profiles, so a colleague's Help change can touch those pagers' dependency sets. The signed-in seller view on a buyer link reads that profile in both `sellerContext` and `currentAvatar`; onboarding's invitation inbox reads inviters' profiles; an open account-deletion modal can read colleague profiles while deciding its mode. These rarer surfaces share the same dependency risk. Company setup intake and appointment writes create the equivalent company-wide risk. Separate frequently changed preferences and setup process data from the access records, then let only the relevant chrome or setup query subscribe to them. Coalescing writes reduces mutation count; separating the records addresses their possible downstream read fanout. Role, ownership, company existence, and deletion must remain immediately authoritative. This is a backend work and invalidation concern, not evidence of one HTTP request for each query.
2. **Opening paths rediscover data already learned earlier in the journey.** Home uses parallel server startup reads and then live counterparts. At audit time, a cold session could request a workspace-role hint alongside the live viewer that would shortly supply the same membership and role; follow-up Phase 4 removed this duplicate read. At audit time, a saved-contract client navigation fetched a title before its live state supplied the same title; Phase 5 removed that client-navigation read. Phase 8 carries the buyer link's authorized template-version ID from page context into its client read owner, allowing immutable content and current state to overlap. Setup booking reads progress and attempt separately, and an ID discovered by either can rebind the attempt read. A shared route-bootstrap contract could carry authorized IDs and small presentation facts into the client read owner as provisional data, start independent immutable reads sooner, and let live subscriptions replace that seed. Apply this per journey rather than merging all live data into a broad query: a combined query can invalidate more often and delay early content behind its slowest branch.
3. **Foreground events are coordinated by individual components.** Linked-contract deal checks, recipient refreshes, buyer-name refreshes, setup completion detection, and setup-call repair each have their own focus or visibility logic. Phase 16 adds a buyer-name client freshness gate, but these owners still coordinate independently. One foreground event source per workspace or buyer session, with resource-specific freshness, single-flight handling, and explicit force-refresh boundaries, would address several findings together. Export, push, revocation, and repair paths still require their own fresh authority rules.
4. **Optional network work has several independent owners.** Destination intent retains Template or New contract reads; Home separately prefetches HubSpot deals and warms visible contract snapshots; support hover can warm Cal availability. Each owner has local limits, but the source shows no shared admission budget across these optional reads. If traces show overlap with foreground work, a workspace-level priority budget could admit navigation and visible content before hover or idle warms, and cancel optional leases when the user changes direction. This is a measurement-led architectural candidate, not a demonstrated bottleneck.

The same dependency issue reaches screens that did not appear as stand-alone round-trip findings: Team's profile/avatar hydration, the persistent HubSpot connection status in workspace scope, the setup prompt on every workspace section, template authoring reads, the setup booking calendar, the signed-in seller's buyer-link chrome, onboarding invitations, and the open deletion modal. A normal live read on those screens is necessary; reevaluating it after an unrelated preference write is the avoidable part. Public buyer-link status and immutable template content have different dependencies and should be evaluated separately.

## Evidence

### Contract selections

- At audit time, [`ContractPersistence.setOption`](../src/lib/contract/persistence.svelte.ts) changed `draftSelections`, checkpointed the journal, and invoked `start()` in the same interaction. `start()` then dispatched `contracts.save` immediately when idle, allowing one mutation per spaced choice.
- Phase 1 changed ordinary choices to reset a 300 ms trailing timer; the journal and local choice still update immediately. `savePending()` skips the timer, and the saved route starts a flush when its editor lease is released. [`ContractEditors.createPersistence`](../src/lib/contract/editors.svelte.ts) still maps each dispatched request to `api.contracts.save`.
- The change should reduce request volume for choice bursts; a production request and latency comparison has not been collected.

### Linked-contract foreground work

- At audit time, [`RepWorkspace.checkDeal`](../src/lib/components/workspace/RepWorkspace.svelte) had only an in-flight guard. Mount, visibility return, and focus each invoked it. The same foreground handler requested `api.hubspotRecipients.request`, and a reactive eligibility effect could request it again.
- Phase 4 uses one visible-and-focused transition counter and one eligibility effect. A linked contract runs at most one foreground pass per transition and installation state. Completed deal checks are reused for 30 seconds and recipient requests for 45 seconds on the same association and installation. Background work is single-flight per destination. The pass waits for live contract state, an admitted interaction, an authenticated connection, and the matching connected HubSpot installation. A new association gets its recipient refresh from `hubspotDeals.link` itself, so the foreground pass skips a duplicate request; an installation or company-read capability change remains a separate refresh trigger. Export, push, and review preflights make a fresh `checkDeal` call even during a background check.
- [`requestBuyerRefresh`](../src/convex/hubspotRecipients.ts) coalesces actual provider refresh jobs by destination, lease, and due time, but the public mutation runs on every client request. Its successful due time is 45 seconds; the new client window is a local upper bound on background request frequency, not a replacement for server authority.
- [`hubspotDeals.check`](../src/convex/hubspotDeals.ts) reads the current destination and, when eligible, calls `readDeal` against HubSpot (lines 461–490). A missing deal is marked unavailable server-side. The export/push check protects a consequential action and should remain authoritative.

### Buyer telemetry

- [`BuyerActivity.clauseOpened`](../src/lib/buyer/activity.svelte.ts) enqueues one event per open (lines 165–190). `drain()` sends each queue entry separately; `send()` posts to `/api/buyer/activity` (lines 192–279).
- Generic pointer, keyboard, or scroll activity has an existing 60-second throttle (lines 144–164). The one opening event is separate from clause events (lines 125–143).
- [`buyerActivity.record`](../src/convex/buyerActivity.ts) validates the current publication, quota, event ID, sequence, and clause on each event (lines 83–220). A batch protocol must preserve per-event outcomes and bounded transactions; batching a client POST alone would not necessarily reduce backend mutation executions.
- Phase 2 adds a maximum of eight ordered clause events per request. `BuyerActivity` waits at most 150 ms for a burst, then posts one batch; the app route forwards it to one Convex HTTP action and `buyerActivity.recordBatch` applies the events in one mutation. Each event keeps its ID and sequence. The mutation reports recorded and unavailable events individually; at the first rate-limited event it defers the remaining events, and the client retries that suffix with the same IDs. Page hide sends pending and in-flight entries with keepalive, relying on receipt deduplication for possible duplicates. The backend still validates publication, clause access, quota, and storage capacity for each event, so a batch reduces request and execution count without reducing per-event validation work. Runtime counts and tail latency remain unmeasured.

### Discussion reply fanout

- The behavior below describes the audit-time code before Phase 6; the progress log records the current implementation.
- [`BuyerDiscussions`](../src/lib/buyer/BuyerDiscussions.svelte) activates the session while the document is active and prepared (line 90). [`DiscussionReadState`](../src/lib/discussions/read-state.svelte.ts) then starts a `discussions.list` live feed (lines 364–380). The same component and read state serve buyer and seller presentations of the buyer document.
- [`DiscussionLayer`](../src/lib/discussions/DiscussionLayer.svelte) renders a `DiscussionThread` for every thread in `session.threads` when the rail is active and unobscured (lines 592–635). [`DiscussionThread`](../src/lib/discussions/DiscussionThread.svelte) immediately acquires and activates that thread's reply stream (lines 26–33); its active condition does not depend on selection or viewport visibility. Each stream registers `api.discussions.replies` (lines 298–316 of `read-state.svelte.ts`).
