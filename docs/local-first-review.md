## Findings

### R1 — Late company-exit cleanup can retire a replacement workspace

**Confirmed; corrected in source; existing automated checkpoint passes. Original finding:** [AuthBridge](../src/lib/auth/AuthBridge.svelte) captures the departing user/session and the draft owner before awaiting the leave operation. The captured draft cleanup correctly becomes inert when that owner has already been retired. The other cleanup still runs against the user's current resources and all of their persisted inventory:

- `workspaceReadResources.forgetMembership(userId)` destroys every currently mounted read owner for that user.
- `contractCacheResources.forgetMembership(userId)` resets the current contract cache whenever its user matches.
- `purgePersistentCaches(entry => entry.userId === userId)` includes a different, newly admitted membership.
- Hint cleanup checks the captured session, but does not distinguish replacement memberships within that session.

If identity or membership changes while the leave mutation is in flight, its late successful response can therefore close a newer workspace's caches and remove newer presentation hints. Old drafts are protected by the captured owner; disposable resources are not. This is a client cleanup ownership bug, independent of whether the server accepts the old leave operation. It should target the departing membership and preserve replacement owners.

Evidence: [AuthBridge](../src/lib/auth/AuthBridge.svelte), [workspace read resources](../src/lib/auth/workspace-read-snapshots.svelte.ts), [contract cache resources](../src/lib/contract/snapshot-cache.ts), [hint retirement](../src/lib/auth/workspace-hints.svelte.ts), and [captured draft cleanup](../src/lib/contract/draft-recovery.svelte.ts).

Recommended correction: carry the departing membership through the company-exit API, capture the retiring resource owners before dispatch, and scope persisted cleanup to that membership. Hint removal must also preserve a replacement membership in the same session. Keep user-wide cleanup for account deletion. Do not make disposable-cache cleanup depend on whether draft cleanup ran: these have separate lifetimes. Implemented resolution: company exit carries membership, captures draft/read/cache/hint owner lifetimes before dispatch, and retires persisted entries and hints by departing membership. Live membership replacement uses the same session retirement boundary. Account deletion uses a separate user-wide resource operation; ordinary disposal closes owners. Same-scope snapshot cache instance recreation is fenced independently of the scoped resource container.

**Deeper cause:** `SessionResources.forgetMembership(userId, sessionId?)` does not express a membership boundary. It serves both company exit and account deletion; read/cache implementations act on currently mounted user-owned resources, while hints additionally check session identity. The leave caller has the departing membership, but the session exit API does not carry it. Correct the resource contract rather than adding separate current-user checks to each implementation. Cleanup needs both the captured mounted owner and the departing persisted scope; account deletion needs its distinct user-wide operation. Membership equality alone also cannot identify a recreated mounted owner. The draft cleanup already captures an owner and is a useful model to preserve, not another defect to fix.

### R3 — Home candidate eligibility remains duplicated

**Maintenance concern resolved; no behavior defect established. Original finding:** [Contracts](../src/lib/components/workspace/Contracts.svelte) and [ContractsCachedResults](../src/lib/components/workspace/ContractsCachedResults.svelte) independently build the memory, disk and startup candidates. [The shared Home selector](../src/lib/components/workspace/home-page.ts) centralizes source priority and authority, but matching a candidate to its query and scope is still repeated in the callers.

Implemented resolution: `retainedHomePages` and `sameHomeScope` now share memory/disk/startup construction and exact scope eligibility with the selector. Keep subscriptions, disk access and each component's live/error/pending fences with their owners. This would make the intended single Home policy easier to maintain; it does not justify adding another storage layer or changing which data is persisted.

### R4 — Home's retention fence assumes stable arrays that Convex does not provide

**Confirmed source defect; corrected in source; existing automated checkpoint passes. Original finding:** Both live Home observation effects in [Contracts](../src/lib/components/workspace/Contracts.svelte) preserve the old `retentionVersion` only when `previous.rows === rows`. The installed Convex SDK's `PaginatedQueryClient.localQueryResultByToken` constructs `allResults` with `concat` on every read. The Svelte adapter calls that read through `getCurrentValue()` on updates. Array identity is therefore not proof of new row content.

The SDK's `loadMoreOfPaginatedQuery` explicitly emits an update when starting a page request. While the next page is pending, this can supply the same existing rows in a new array with `LoadingMore`. After `invalidateHome`, Home sees a different array, stamps the current cache version, and calls `rememberBrowse` with those unchanged rows. This defeats the intended protection against status-only updates refilling invalidated memory. The buyer disk confirmation branch also uses this freshness decision, although ordinary load-more sets `buyerPaged` and skips that branch.

This concerns retained presentation after invalidation, not the authority of the mounted live subscription. Keep that distinction when fixing it. The initial recommendation was to compare stable row content within the same query/scope. Deeper tracing shows that this is useful for deduplication but does not by itself establish server freshness: a valid new observation can have identical visible rows, and a subscription retry need not reset the adapter's previous result through `onArgsChange` alone. The observation effect and read owner also divide responsibility for the version fence. Resolve the retention policy and its ownership first, then share the implementation across both lists. Avoid creating an additional query or a persistent directory merely to obtain freshness. Implemented resolution: `observeHome` leases belong to a scope/query/subscription-attempt lifetime. The read owner rejects disposed/replaced producers and LoadingFirstPage/LoadingMore retention writes; admitted matching settled deliveries can retain provisional pages. Content equality deduplicates memory and disk payloads. Invalidation removes existing seeds and cancels scheduled writes while the mounted live source remains authoritative. SDK lifetime findings and the revised recommendation follow below.

Evidence: `src/lib/components/workspace/Contracts.svelte` buyer and contract observation effects; installed `node_modules/convex-svelte/dist/use_paginated_query.svelte.js`; `node_modules/convex/src/browser/simple_client.ts` (`getCurrentValue`); and `node_modules/convex/src/browser/sync/paginated_query_client.ts` (`localQueryResultByToken`, `loadMoreOfPaginatedQuery`). Existing Home checks use a mock pager; their passing result does not establish this SDK identity assumption. The architecture previously claimed that status-only updates could not refill invalidated seeds; that claim now explicitly records the incomplete fence and links to this finding.

**Adjacent lifetime problem:** the component stores observation provenance, while `WorkspaceReadSnapshots.rememberBrowse` accepts only rows/query/pagination and stamps whichever version the owner currently has. The owner cannot reject a stale producer independently. A route remount resets the component's observation history while the scoped read owner survives. SDK disposal tracing does not establish a separate stale-remount defect: the SDK removes paginated and underlying local subscriptions when their last subscriber leaves. The confirmed concern is the split contract and the missing provenance argument, not a claim that remounts always replay stale rows.

Successful direct Convex mutations synchronize subscription results with mutation completion; the implementation already accounts for live rows arriving before save callbacks. A content-only fence could therefore reject an already updated observation after the callback invalidates retention, or refuse to retain an equal but newly confirmed page. Content comparison belongs to write deduplication. Cancellation/write epochs belong to local work ownership. Neither should be described as a server revision or access proof. Subscription attempts, scope matching and current live authority need explicit treatment when simplifying this policy.

**Publication is an adjacent boundary to handle differently:** [BuyerLinkController](../src/lib/buyer/links.svelte.ts) publishes with `client.action(api.buyerLinks.ensureLatest, ...)`, then calls the same Home invalidation mechanism on confirmed creation, including late delivery. The SDK's `RequestManager.onResponse` explicitly resolves actions independently of query synchronization; only successful direct mutations wait for the corresponding transition timestamp. Action completion must not be used as proof that an existing Home subscription already includes the published link. This does not establish a server publication defect or a second authorization issue; it rules out applying a mutation-completion shortcut indiscriminately to Home retention.

### R5 — Malformed registry metadata has no recovery path

**Confirmed recovery gap; corrected in source; existing automated checkpoint passes. Original finding:** In [the persistent registry](../src/lib/auth/persistent-cache-registry.ts), `register` refuses a database when its key exists but cannot be parsed/validated. `listPersistentCaches` omits that entry. `discoverLegacyCaches` skips every name with an existing key, explicitly including malformed inventory. Registered deletion also needs a valid entry/deletion marker. Consequently invalid JSON, an oversized record or a schema-invalid record can permanently disable that disposable database and exclude it from routine retirement/pruning even when browser storage and Web Locks are working.

This is a cache availability/reclamation problem, not a loss of draft intent or an access bypass. Failing closed for access is correct; leaving recoverable disposable state permanently stranded is the missing part. Add one recovery path for malformed metadata in the recognized deployment's disposable namespace. Discard/rebuild the unusable cache under the same metadata/access coordination as normal deletion, preserve in-flight native-open ownership, and do not infer a user/membership from a database name. Keep this separate from legitimate API unavailability, where optional disk absence remains the intended fallback. Do not introduce a generic migration framework or another inventory store.

**Deeper cause:** valid ownership metadata and deletion coordination are coupled to the same fully validated record. When ownership parsing fails, the registered path cannot represent safe reclamation without inventing an owner, and legacy discovery correctly refuses to bypass that path. Keep one registry, but let a validated disposable database address and pending deletion state coordinate recovery without claiming a valid user/membership. User/membership targeting must still require valid ownership metadata. Recovery discards unusable disposable data rather than repairing application payloads. Implemented resolution: the existing registry can persist an ownerless recovery deletion marker for a validated deployment-scoped disposable address. Malformed record scanning and optional legacy discovery route through the same metadata/access locks and matching-marker native-success removal. Registration remains unavailable while marked; a later owner/use can rebuild after deletion. Recovery scanning works without native database enumeration. The metadata-lock recheck and pending retry mode preserve valid ownership rebuilt by another tab before a corruption cleanup runs or retries. No second inventory or inferred user/member was added.

## Recommended end state

The storage categories are appropriate. The deeper problems are contracts between owners, not insufficient local storage. Keep Convex authority, disposable warm presentation/immutable snapshots, and separately owned recoverable draft intent. Improve these boundaries together:

1. **One explicit retirement contract.** Separate membership departure, user/account deletion and ordinary owner disposal. Capture mounted owner instances and departing identity before asynchronous work; clean persisted inventory by the departing scope. Reuse that boundary for live membership replacement and explicit company exit so they cannot drift. Session-matched hints must additionally preserve a replacement membership. Account deletion remains user-wide. Preserve the existing captured draft owner and native access leases.
2. **One Home retention policy, with an intentionally modest guarantee.** Recommend keeping retained pages provisional rather than building a causal freshness protocol for warm presentation. Invalidation should remove existing affected seeds and cancel obsolete scheduled writes. Only admitted, matching, settled live observations should supply new retained pages; content comparison should deduplicate payloads, not certify freshness. A pagination loading transition alone should not cause a retained write. Scope/attempt disposal must reject obsolete producers in the owner. A retained page still cannot declare definitive emptiness, current unread state or permission to fetch more. Explicitly drop the unsupported guarantee that a retained result necessarily includes the latest action's commit. If that stronger user-facing guarantee becomes necessary, it requires explicit server provenance/settlement, not array identity, JSON equality or a timer.
3. **One shared Home candidate builder.** Put source eligibility, exact-query/scope matching and retained observation rules with the page policy/read owner. Keep live subscription lifetimes and lightweight fallback rendering separate. Do not create a universal storage manager combining drafts, document bytes and route display state; their authority and retention needs differ.
4. **Recover disposable corruption through the existing registry.** Add coordinated discard/rebuild for malformed metadata; retain the existing fail-open-to-live behavior when optional APIs fail. This belongs with the ownership cleanup work because it uses the same marker/access-lock/native-deletion rules. Preserve successful deletion semantics and late native-open ownership.
5. **One grouped verification checkpoint with honest coverage.** Maintain affected existing fixtures so they reflect actual SDK deliveries and preserve their assertions. Existing performance checks remain required for caching corrections. Separate native/browser acceptance from mocked guarantees and production measurement; neither can be inferred from a passing build. No new tests or browser automation are authorized in this audit.

The implemented correction deliberately simplifies the Home freshness promise. A settled update with equal rows can be retained provisionally after invalidation; equality never proves the latest command is represented. Do not merge physical databases solely to simplify names, add local directories/offline queues, move drafts into disposable eviction, or use access freshness to govern cached presentation. The review has not found evidence requiring those changes.

## Correction order

1. Fix R1's ownership boundary first. A leave response must clean only the departing membership and captured owners, including hints and persisted inventory; account deletion retains its separate user-wide scope.
2. Apply R4's modest provisional retention contract in one owner. Reject obsolete producers and status-only retention writes, deduplicate content, and keep live authority independent of retention versions. Do not claim that action completion, equal rows or a new array proves post-change freshness.
3. Consolidate R3's pure candidate eligibility while touching Home policy. Preserve the components' distinct subscriptions and loading/error behavior.
4. Add R5's coordinated recovery for malformed disposable registry records while keeping storage failures optional.
5. Group validation after those corrections. Preserve existing automated guarantees, run the required performance suite for caching changes, and separately record the browser/native scenarios that remain unverified. Do not count existing mock checks as new branch coverage.

Keep the overall local/Convex split. The source review has not established a reason to add or remove another storage category. These follow-up corrections need clearer ownership and one shared Home policy. R1/R3/R4/R5 application corrections and their existing automated checkpoint are complete; native acceptance remains unverified.

## Grouped acceptance scenarios for the corrections

These are acceptance criteria for the grouped validation checkpoint, not new tests or results. Preserve existing assertions/fixtures; native/browser checks remain user-led.

| Boundary | Behavior the checkpoint must establish or explicitly leave unverified |
| --- | --- |
| Departure versus replacement | A late successful leave cleans captured owners and departing inventory, preserving a newer membership's caches/hints/drafts in the same user/session. Recreated mounted owners are distinguished from old instances. |
| Departure versus deletion | Failed/canceled departure retains intent. Confirmed account deletion still removes affected-user inventory/journals, including unmounted records. Ordinary teardown only closes owners. |
| Home retention versus live authority | Real SDK-style fresh arrays with unchanged rows and loading transitions cannot masquerade as a server revision. Empty/shorter live pages still win; retained pages cannot authorize unread state, emptiness or pagination. |
| Home command settlement | Direct-mutation updates arriving before invalidation, action publication arriving before query refresh, retries, query changes and route remounts obey the modest provisional policy without stale producer writes or extra freshness queries. |
| Registry recovery versus native ownership | Invalid JSON/oversized/schema-invalid metadata can recover without deleting an unrelated namespace. Blocked/late native opens retain their leases until terminal events; successful cleanup removes only matching markers. |
| Evidence versus speed | Existing save/replay/revision, scheduling, cache reuse and recovery guarantees remain checked by required existing suites. Native acceptance and real performance remain separately recorded; no production speedup is inferred. |
