# HubSpot integration

## Behavior

An Admin installs one account-level OAuth connection per company. The existing Admin role policy is unchanged. Other current company members can browse that account's accessible deals; individual HubSpot employee permissions are not mirrored.

Once HubSpot is installed, contract creation requires the live searchable deal picker. Companies without an installation retain manual naming. Reconnect requirements and disabled provider/delivery flags do not permit manual creation. All nonarchived deals can be linked, including closed-stage deals, provided another current contract in the same company and HubSpot account does not already own the deal. An unavailable link still reserves its deal. Deletion or replacement releases that contract’s current ownership; historical activity and receipts do not reserve deals. Default browsing requests one window of 12 recent candidates, ordered by creation date with newest first, and shows up to three unlinked deals. This window can show fewer than three or zero results even when older eligible deals exist; search finds older deals. Search queries the full connected account and returns the newest three matches, including linked matches. Linked search results are grey and cannot be selected; a separate, keyboard-focusable info icon explains: “This deal is already linked to another contract.” When more matches exist, the picker asks users to refine their search. Browsing and search both use HubSpot's search endpoint, so newly created deals can take a few moments to appear. The server copies the exact verified deal name into the existing `buyerCompanyName` title field. It does not substitute legal-party text or continuously rename the contract. Existing unlinked contracts remain readable and deletable, but must be explicitly associated before new edits, reviews or downloads. First association copies the selected deal’s verified name into the contract title and preserves its content; no match or historical activity is inferred.

The creation and relink pickers share one in-memory browse page per authenticated workspace. Home warms the 12 recent browse candidates after its primary surface paints, only for a visible tab, an available contract template/instructions and an enabled, connected installation. Hovering, focusing or touching New contract starts the same request without waiting for background warming. Opening a cold picker and clearing search load immediately; typing retains a 250 ms debounce. Successful browse results are reused for 45 seconds, then remain visible while refreshed; search results only share in-flight requests. Nothing polls HubSpot. Session, company, transport and installation changes clear retained data and fence obsolete requests. Reconnects invalidate the page using installation time rather than OAuth token generation. Speculative errors are not cached. Provider pages contain metadata only. While a picker is open, a bounded live local query checks candidate and selected IDs against the compact contract directory. Link, delete and replacement changes update eligibility without another provider request. Unknown or failed eligibility disables new selection and submission; local query failure offers reload recovery. Creation and relinking still verify the chosen deal on the server.

Link commits check canonical current ownership transactionally, scoped to company, account and deal; only the authorized target contract is excluded during repair. Competing attempts cannot add another owner. Accepted operation receipts replay before provider and ownership checks and continue resolving the original contract or its deletion. A rejected occupied-deal operation records a terminal `hubspot:deal-already-linked:v1` refusal in the create/relink receipt namespace, then the action emits the structured `hubspot-deal-already-linked` error. The mutation returns rather than throwing so the refusal remains durable. A retry of that identity stays refused even after the deal is released. This specific refusal safely unlocks an uncertain client request for a new choice and fresh operation identity; other uncertain requests retain their frozen identity and arguments. Live eligibility changes never discard a busy or frozen request, because the observed owner may be its own accepted operation with a lost response.

CRM Notes record only creation, accepted concession applications, actual approval requests, explicit approvals/declines and browser download initiation. Applying as an Admin emits one application note, without a separate automatic approval note. Removals, renames, deletion, review completion/reopening and relinking emit no note. Deliberately repeating a same-status decision counts; retrying its operation does not. An approval email retry does not create a new approval request activity.

Notes include the original actor, action time and contract link. Files are uploaded PRIVATE and attached to the download note. No HubSpot Custom Events or App Events are configured.

A confirmed deleted, archived or inaccessible deal blocks new edits (including renames), approval requests/decisions, review completion/reopening and downloads until another deal is linked. Reading, deletion and repair remain available. While blocked, the contract’s name, content, approvals and unsaved drafts stay intact. The open contract offers **Link another deal** in a styled notice above the document; contract cards do not show deal-link callouts. The same picker supports first association and replacement. Any current company editor can use the shared picker to choose a replacement in the same connected account. The generation-checked repair updates the deal link and copies the selected deal’s verified name into the contract title, preserving content, edit/review revisions and directory order. Future accepted activity uses the replacement; historical rows, retries and already reserved download attempts retain their original destination. No history is copied or backfilled. Durable generation blocks also survive ordinary local contract deletion. Accepted-operation retries and acknowledgments of already initiated downloads still resolve their original work. Temporary outages, credential reconnects, rate limits and disabled delivery leave prior deal availability unchanged; otherwise eligible local work can continue. Bounded direct checks on editor entry/foreground resumption and explicit review/download starts complement delivery observations. Mutations enforce recorded availability transactionally, so external changes have detection latency; no provider call occurs per keystroke. Generic 403/scope failures, invalid names and omitted search results do not establish deletion.

## Development setup and activation

The registered development app and its Auth tab are linked in [hubspot/README.md](../hubspot/README.md). The backend is `dev:disciplined-squid-496`. Production is separate and requires an explicitly authorized release.

Set these backend environment variables on the intended deployment. No credential belongs in a `PUBLIC_` variable, source file, URL returned to a browser or log.

| Variable                   | Purpose                                                                       |
| -------------------------- | ----------------------------------------------------------------------------- |
| `HUBSPOT_CLIENT_ID`        | Registered OAuth app identifier                                               |
| `HUBSPOT_CLIENT_SECRET`    | App's OAuth client secret; set through Convex's dashboard or CLI stdin        |
| `HUBSPOT_REDIRECT_URI`     | Exact registered callback, e.g. `http://localhost:5173/api/hubspot/callback`  |
| `HUBSPOT_SCOPES`           | `oauth crm.objects.deals.read crm.objects.deals.write files.read files.write` |
| `APP_URL`                  | Website origin used by note links                                             |
| `HUBSPOT_ENABLED`          | Set `true` to permit Install and deal selection                               |
| `HUBSPOT_DELIVERY_ENABLED` | Set `true` separately after provider checks, to dispatch queued activity      |

The development client ID and secret are configured, and `APP_URL` matches the local callback. Account `343876639` is installed. Installation and delivery are enabled on development after the provider checks below. For a new deployment, use Install as an Admin and approve the requested permissions in HubSpot; keep delivery disabled until its provider checks pass. Denied, expired or replayed installs preserve a prior working connection. Reconnect must use the original account.

The CLI's personal access key is used for app registration only; it is never a customer integration token. OAuth credentials are stored in server-only tables with single-use hashed OAuth states, browser correlation cookies, current membership checks, credential generations and refresh claims. Public status queries return no tokens. A refresh with an unknown response may require reconnecting rather than guessing the rotated credential.

File recovery searches use an 18-character prefix because the provider rejects long name filters; complete filename, privacy and byte/hash checks still determine adoption. A missing search result never authorizes a resend. These checks cover one installed Admin account, not every viewer role, provider limit or injected failure scenario.

## Delivery, identity and recovery

All saves carry one ordered recoverable command journal with stable interaction IDs and one immutable in-flight batch, whether or not HubSpot is installed. Up to 25 commands are validated sequentially and committed atomically. Intermediate applications are retained even if later replaced or removed. Snapshot reads are shared within the batch; removals emit nothing and need no template reads. The journal is bounded at 250 commands and never compacted by discarding activity. Committed receipts resolve before stale edit conflicts and policy gates, including after another editor’s changes or later installation. Uninstalled companies produce no CRM activity. Empty unchanged saves remain zero-write acknowledgments.

Fresh snapshots without commands are rejected with reload/recovery guidance; retained legacy requests can acknowledge their last accepted operation, conflict against newer state or acknowledge an unchanged no-op. Journal v6 writes commands universally; v4/v5 readers retain old drafts and immutable requests. Ambiguous superseded snapshot outcomes are not reconstructed as activity. Association blocks are distinct from transport failures: drafts remain pending, controlled accepted-request resolution remains possible, and authoritative repair resumes eligible work without clearing unrelated errors. All new approval requests/decisions require operation identities/protocol, and all new exports use stable attempt identities.

`hubspotEvents` is the durable local outbox. Each activity runs independently through a direct Workpool with parallelism five and action retries disabled; only the outbox chooses retries. Enqueue and the event's work/execution identity commit atomically. Completion and recovery match that identity; stale callbacks cannot restart terminal or replacement work. Upload precedes Note creation only within its download. Original `hs_timestamp` determines timeline chronology. Delivery starts are swept each minute. A five-minute claim plus a 30-second retirement reserve fences abandoned work. Company retirement cancels queued work and waits for started claims; cancellation alone does not stop a running action.

Admission, claim, fresh dispatch and settlement share one evidence policy. Permanently unavailable/replaced undispatched history is `paused`, outside the active sweep. Credential-only `blocked` rows recover through bounded sweeps. A retained dispatch has reconciliation precedence over link repair/pause: it can observe only its original destination. Positive File adoption records the original upload, but cannot authorize a new Note on an unavailable or replaced generation. Ordinary contract deletion preserves accepted history; a missing directory projection falls back to the source contract transactionally.

Claims recheck company/account/credential/link fences before dispatch. Every creation request has a unique persisted dispatch identity. A proven local pre-fetch denial clears only the matching invocation's definitely unsent intent; a provider-returned 429 or a failed reconciliation read never clears an older intent. Unknown post-intent errors remain ambiguous. Current credential generation is checked before storing a generation block or changing shared availability; stale failures cannot install hidden blocks. Current provider 401 observations, including deal browsing without outbox work, use the same fenced Reconnect transition. Other errors do not imply invalid credentials. Positive historical success settles its own row without clearing current unavailability. Contract/company changes never retarget history.

A timeout, lost response or unclassified failure after an attempted write becomes `uncertain`. The worker adopts only positive evidence: matching Note markers in associated Notes, or a deterministic PRIVATE filename plus exact length and SHA-256. A pass covers at most five association pages of 100 Notes, or 100 File candidates. Dispatch-keyed checkpoints retain the current page/candidate IDs, attempted frontier, cursor and bounded unresolved count. A member-local missing/failed read does not suppress later positive members. Completed unresolved passes search again; a partial/absent pass never proves noncreation.

Reconciliation uses bounded **serial** reads, without relying on an unverified Notes batch API. One invocation permits at most 12 HTTP requests, 150 seconds elapsed before its reserve and 64 MiB of candidate body verification. It starts a request only with 30 seconds of segment reserve; a complete File metadata/signing/body unit reserves three requests and 80 seconds. Body reads have a 25-second abort and stream length cap. The five-minute claim leaves additional time for RPC/checkpoint/settlement work. Larger File candidates remain unresolved for operator attention rather than permitting unbounded reads. These are conservative execution bounds, not measured throughput improvements; a complete worst-case serial Note pass still costs up to 505 provider reads.

The automatic horizon is the original dispatch time plus 24 hours. Admission, pauses, yields and failure settlement retain `attention` at that horizon; no retry resets it. Positive results already returned can still settle matching bookkeeping. Exactly-once delivery is not promised. An authenticated direct deal read returning 404 marks only its matching generation unavailable; generic failures, search omissions, 429s and revoked credentials do not imply deletion.

Operators inspect `hubspotEvents` in the intended Convex deployment, using event IDs and sanitized diagnostics. Avoid exposing connection tokens. `hubspotOperations:recover` is internal-only and requires an evidence reference. `disposition: "reconcile"` authorizes one bounded original-dispatch observation segment, including after repair or the automatic horizon. It consumes that authority once without resetting the horizon or permitting a resend. Failed or incomplete work beyond the horizon returns to attention. `"confirmed-not-sent"` clears its dispatch marker only after the operator has established noncreation and recorded evidence. Never use this to guess that an ambiguous Note/File does not exist. Link-generation blocks still apply. No automatic deletion of HubSpot history is performed.

## Downloads and retention

A stable export attempt captures the original destination, title, immutable version, choices and approval generations at reservation. Concurrent preparation is fenced; retries return the adopted bytes. Reservation and release enforce association eligibility; release also rechecks current content and approval state after generation. Relinking does not retarget or rename an attempt that already captured a destination and title. A pre-install reservation with no destination cannot be newly released after installation: its client initiation identity is retired so the next eligible download reserves a fresh attempt. Acknowledgments already journaled after initiation retain their original identity and destination. Preparation alone creates no download activity.

After successful fetch, Blob read and anchor initiation, the browser stores a per-attempt, deployment/member-scoped acknowledgment and asynchronously commits it once. Individual storage keys prevent concurrent tabs overwriting each other's acknowledgments. Recovery snapshots keys before reading/removing them, isolates malformed/terminal entries and persists server-directed future deferral on the original entry and excludes deferred/future-dated entries before its 25-eligible-attempt limit. Terminal too-early timestamps are retired from automatic recovery without changing their original value; account/session/transport failures preserve pending entries. Workspace recovery retries after reload/transport failure independently of optional snapshot caching. Browser initiation cannot prove a disk save; a crash before journaling or unavailable browser storage remains an observation gap.

The application permits local retry only through **reservation time plus one hour**, even after an early upload or Note succeeds. That retry returns the identical adopted blob; it never re-prepares an expired identity. Unlinked acknowledgment adds no attachment hold. A linked acknowledgment with still-eligible retained bytes adds an upload hold through the first server acknowledgment time plus 30 days; replay does not extend it. A confirmed private upload or positive File adoption records remote identity and ends that hold independently of Note completion. Ambiguous uploads retain the bounded hold. Confirmed remote identity can attach even after local bytes are gone.

Retrieval/upload eligibility is distinct from physical cleanup. The attempt remains a storage owner until its last necessary hold plus a **15-minute physical read grace**, then the bounded five-minute expiry sweep releases the reference and checks competing owners in the same transaction. Confirmation after an older deadline permits a fresh physical grace for an already in-flight bounded provider read, without restoring expired eligibility. This grace covers the sender's bounded retrieval path and ordinary browser transfers; it does not promise arbitrary-duration browser reads or immediate physical deletion at the eligibility deadline. No supported atomic storage-read/delete guarantee is assumed. The independent 24-hour orphan sweep recognizes attempt ownership.

Complete immutable provenance remains until company deletion: ordered item/concession IDs, optional original review application IDs/statuses, template/edit/review generations, actor/title/destination, attempt/release/acknowledgment facts, filename/hash/size and remote identity. Selection chunks use one compact ordered tuple representation for preparation and permanent identity; no redundant verbose selection is written. Receipt chunks are separate and retained. A valid late acknowledgment still records one truthful event with missing attachment when neither eligible bytes nor verified remote identity exists.

Ordinary contract deletion retains accepted company history. Company deletion removes credentials first, cancels queued Workpool work, waits for bounded started actions, and retires events, attempts, file holds, generation blocks, receipts, chunks and OAuth states through bounded phases. Previously written HubSpot records are retained.

## Executor and provenance cutover

The development cutover on 2026-11-06 paused delivery and inventoried the complete legacy component, independent of event pointers: zero application events/exports; zero Workflow rows/steps/events/callback failures/scheduled functions; zero nested Workpool work/payload/queues/running state/scheduled functions. Consequently there were no tokenless calls, callbacks, cleanup continuations or legacy export representations to convert, and the Workflow mount/dependency was removed. Inventory evidence is retained in `/tmp/oceans-hubspot-remediation/legacy-inventory.json`. This is a development-specific empty-state cutover, not a migration for a populated deployment.

Do not deploy this executor/provenance change to a populated older deployment without first installing compatible token-bearing/tokenless legacy readers and callbacks, then performing a bounded component-wide drain and converting terminal export chunks from their own original data. Never let a tokenless legacy call claim new Workpool work. Zero app pointers or Workflow rows alone cannot establish drain; include nested work, callback failures and scheduled cleanup continuations. Keep dispatch disabled if visibility is incomplete. A rollback must understand new work/dispatch identities, paused status, tuple provenance and independent holds; use a compatible forward repair if necessary. Never restore uncertainty as an undispatched operation.
