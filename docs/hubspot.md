# HubSpot integration

## Behavior

An Admin installs one account-level OAuth connection per company. The existing Admin role policy is unchanged. Other current company members can browse that account's accessible deals; individual HubSpot employee permissions are not mirrored.

Once HubSpot is installed, contract creation requires the live searchable deal picker. Companies without an installation retain manual naming. Reconnect requirements and disabled provider/delivery flags do not permit manual creation. All nonarchived deals can be linked, including closed-stage deals, provided another current contract in the same company and current HubSpot installation does not already own the deal. An unavailable link still reserves its deal. Deletion or replacement releases that contract’s current ownership; historical activity and receipts do not reserve deals. Default browsing starts with 12 recent candidates from HubSpot's search endpoint, ordered by creation date with newest first, and shows up to three unlinked deals. If none are available, it automatically browses the full objects list until it finds an unlinked deal or exhausts the list, even when the recent search has no further pages. Search queries the full connected account and returns the newest three matches, including linked matches. Linked search results are grey and cannot be selected; a separate, keyboard-focusable info icon explains: “This deal is already linked to another contract.” When more matches exist, the picker asks users to refine their search. Newly created deals can take a few moments to appear in search; search exhaustion alone does not establish full-list exhaustion. The server copies the exact verified deal name into the existing `buyerCompanyName` title field. It does not substitute legal-party text or continuously rename the contract. Existing unlinked contracts remain readable and deletable, but must be explicitly associated before new edits, reviews or downloads. First association copies the selected deal’s verified name into the contract title and preserves its content; no match or historical activity is inferred.

The creation and relink pickers share one in-memory recent page per authenticated workspace. Home warms the 12 recent browse candidates after its primary surface paints, only for a visible tab, an available contract template/instructions and an enabled, connected installation. Hovering, focusing or touching New contract starts the same request without waiting for background warming. Opening a cold picker and clearing search load immediately; typing retains a 250 ms debounce. Successful recent results are reused for 45 seconds, then remain visible while refreshed; search and continuation pages only share in-flight requests. If the recent candidates contain no available deal, the picker automatically browses the full deal list in 12-candidate pages, yielding 250 ms between requests, until it finds an unlinked deal or exhausts the list. This continuation uses the objects API to avoid the search API's result cap. Only exhaustion displays “No unlinked HubSpot deals available”; request failures retain retry recovery. The pickers do not poll HubSpot; the optional backend lifecycle Journal reader runs separately. Session, company, transport and immutable connection ID changes clear retained data and fence obsolete requests. Reconnects invalidate the page using installation time rather than OAuth token generation. Speculative errors are not cached. Provider pages contain metadata only. While a picker is open, a bounded live local query checks candidate and selected IDs against the compact contract directory. Link, delete and replacement changes update eligibility without another provider request, advancing browsing if the current page becomes fully linked. Unknown or failed eligibility disables new selection and submission; local query failure offers reload recovery. Creation and relinking still verify the chosen deal on the server.

Link commits check canonical current ownership transactionally, scoped to company, immutable connection ID and deal (the connection fixes the account); only the authorized target contract is excluded during repair. Competing attempts cannot add another owner. Accepted operation receipts replay before provider and ownership checks and continue resolving the original contract or its deletion. A rejected occupied-deal operation records a terminal `hubspot:deal-already-linked:v1` refusal in the create/relink receipt namespace, then the action emits the structured `hubspot-deal-already-linked` error. The mutation returns rather than throwing so the refusal remains durable. A retry of that identity stays refused even after the deal is released. A permanently removed target records `hubspot:installation-retired:v1` and emits `hubspot-installation-retired`. Both the prepare and final commit mutations read the receipt before checking target lifetime, so acceptance and terminal refusal serialize. Either durable refusal safely unlocks a client request for a new choice and fresh operation identity; generic failures retain their frozen identity and arguments. An error during provider work rechecks the atomic outcome before surfacing a transient failure. Live eligibility changes never discard a busy or frozen request, because the observed owner may be its own accepted operation with a lost response.

CRM Notes record only creation, accepted concession applications, actual approval requests, explicit approvals/declines and browser download initiation. Applying as an Admin emits one application note, without a separate automatic approval note. Removals, renames, deletion, review completion/reopening and relinking emit no note. Deliberately repeating a same-status decision counts; retrying its operation does not. An approval email retry does not create a new approval request activity.

Notes include the original actor, action time and contract link. Files are uploaded PRIVATE and attached to the download note. No HubSpot Custom Events or App Events are configured.

A confirmed deleted, archived or inaccessible deal blocks new edits (including renames), approval requests/decisions, review completion/reopening and downloads until another deal is linked. Reading, deletion and repair remain available. While blocked, the contract’s name, content, approvals and unsaved drafts stay intact. The open contract offers **Link another deal** in a styled notice above the document; contract cards do not show deal-link callouts. The same picker supports first association and replacement. Any current company editor can use the shared picker to choose a replacement in the same connected account. The generation-checked repair updates the deal link and copies the selected deal’s verified name into the contract title, preserving content, edit/review revisions and directory order. Future accepted activity uses the replacement; historical rows, retries and already reserved download attempts retain their original destination. No history is copied or backfilled. Durable generation blocks also survive ordinary local contract deletion. Accepted-operation retries and acknowledgments of already initiated downloads still resolve their original work. Temporary outages, credential reconnects, rate limits and disabled delivery leave prior deal availability unchanged; otherwise eligible local work can continue. Bounded direct checks on editor entry/foreground resumption and explicit review/download starts complement delivery observations. Mutations enforce recorded availability transactionally, so external changes have detection latency; no provider call occurs per keystroke. Generic 403/scope failures, invalid names and omitted search results do not establish deletion.

Contract settings replaces manual name editing with a read-only name and **Link another deal** while HubSpot is installed. Contracts without a link to the current installation offer **Link a HubSpot deal**. Both actions reuse the generation-checked relink picker above; unavailable deals can still be replaced. Reconnect requirements and disabled integration flags disable deal selection without falling back to manual naming. Unknown or failed installation reads also keep manual naming unavailable and offer retry on failure. Uninstalled or uninstalling workspaces retain the normal editable name and Save action.

## Buyer-link recipient

The contract footer uses the linked deal's associated company as its recipient, while the contract title remains the verified deal name or the user's later rename. A HubSpot link remains the source indicator after a title rename. Unlinked contracts use their contract name. The server resolves the unique HubSpot-defined primary company (deal-to-company type 5), otherwise the sole distinct associated company. Missing, blank, archived or ambiguous company data uses “the customer”; a nameless primary never selects a secondary company. Associations are read completely within a five-page budget, with repeated cursors and malformed or incomplete responses treated as indeterminate.

Recipient metadata belongs only to the open contract view, separate from saved content, revisions, directory state, approvals, exports and buyer-link snapshots. It loads independently on open/link changes and visible focus/visibility resumption, reusing successful or authoritative-empty observations for 45 seconds. A stale refresh clears the old name; transient errors honor bounded cooldowns and retry on the next eligible event. There is no polling or continuous-focus synchronization. Session, transport, link generation, installation time and current request ownership fence obsolete results; authorization and the current target are rechecked server-side after provider reads. Company lookup failures never mark the deal unavailable or gate Copy link, saving or exports.

Company naming requires the explicit `crm.objects.companies.read` grant. Missing grants leave normal deal/delivery capabilities connected; the footer falls back and admins can use **Reconnect** in the HubSpot integration details. Register the manifest's Companies read scope before adding it to `HUBSPOT_SCOPES` and requesting consent. Existing tokens do not gain scopes through refresh. Verify real company access and retained Quotes grants during reauthorization; checked-in config and automated checks do not prove provider consent or endpoint access.

## Uninstall and reinstall

A current workspace admin can choose **Uninstall HubSpot** on the integration detail page even when credentials require reconnect or installation/delivery flags are disabled. The confirmation explains that HubSpot disconnects for the workspace while contracts, approvals and previously sent activity stay. The admin must type `uninstall HubSpot` before submitting, using the same typed-confirmation pattern as account deletion. If another local workspace still uses the account, the confirmation explains that it stays connected, without naming the other tenant.

`hubspotUninstall:uninstall` is a local mutation, idempotent by immutable connection ID. It marks the connection `retiring`, advances the durable `hubspotLifecycles` version and schedules bounded cleanup. Manual creation, editing, review and downloads are immediately available; no healthy credentials are required for local removal. Old OAuth states cannot commit after the version changes, even once the credential row is deleted and its generation would otherwise return to zero. Accepted command receipts remain authoritative.

The worker permanently retires pending/blocked/paused/uncertain events for that installation, cancels queued Workpool work, and waits for existing claims plus their request reserve. It preserves dispatch uncertainty and truthful late positive results. It releases integration-specific upload holds with the existing physical read grace, preserving local retry eligibility and original provenance. New downloads have no CRM destination. A late acknowledgment of an older initiated download still records acknowledgment facts but cannot create a new event or upload hold for a removed installation. No Note/File deletion or backlog replay is performed.

When the workspace is the last active local attachment, a server-only worker attempts `DELETE /appinstalls/2026-09/external-install` using narrowly scoped teardown credentials. It handles empty `204` as confirmed. Shared-account lookups and a durable removal lock fence new local installation commits while teardown runs. Existing token refresh claims retire before teardown refresh. Tokens never appear in scheduled arguments, client status or logs; credentials are purged after bounded teardown. Tenant removal history and account provider authority have separate lifetimes: `hubspotRemovals` owns local progress; `hubspotAccountRemovals` alone owns provider outcome, dispatch authority and account locks. Public status joins them. Before full-company cleanup erases local history and credentials, it detaches each account operation in the same transaction domain as final DELETE authorization. A never-authorized operation becomes unable to dispatch. An already-authorized/unknown operation survives with only account ID, an opaque operation correlation, outcome/times and diagnostic; it retains no company/actor/content/tokens. Bounded recovery and late results work without the tenant. Known settled detached operations are removed safely; unresolved operations remain fenced.

Provider outcomes are separate from local removal: `confirmed`, `shared`, `attention` (a definite refusal or credentials unavailable), or `unknown` (an ambiguous external outcome). Timeouts/5xx are not success and are never automatically resent. A crash after dispatch is recovered without another DELETE. Ambiguous outcomes retain the nonsecret account lock after purging secrets; the UI explains local removal and links to HubSpot uninstall instructions. A verified Journal uninstall can resolve that lock. Otherwise an operator verifies removal directly in HubSpot and uses internal `hubspotUninstall:reconcile` with the account-operation ID from `hubspotAccountRemovals` and a concise evidence reference, after its bounded request lease has elapsed. This records confirmation; it never sends another uninstall request. Do not use it merely to dismiss an error or to guess that an old request cannot still finish.

Local guards cannot prevent independent consent/reinstall inside HubSpot or retract an already-started HTTP request. Newer Journal install evidence prevents an old worker from beginning DELETE; ambiguous old/new chronology needs reconciliation rather than destructive retries. Reinstall is unavailable during active/ambiguous teardown. Once safe, a fresh OAuth install receives a new connection ID; reconnect preserves its existing ID. Old contract links remain historical and impose no requirements while uninstalled. The ordered live contract subscription owns client work policy; partial save replies and delayed deal-check responses cannot replace it. A refused save retains its immutable request without blind retries, and can retry after a live policy transition or the existing retry action. Accepted local download attempts keep their original member, bytes, filename and one-hour retry window even across reinstall; fresh downloads still require the current association. After a fresh install they require explicit linking, retain increasing link generations and reserve no current deals. Both canonical and directory ownership queries include the installation before applying bounded limits. New clients freeze the expected connection ID in create/relink requests; older clients without it cannot start new link writes after an uninstall, while accepted receipts still replay first.

### HubSpot-side uninstall detection

The optional `hubspotJournal` consumer uses app client-credentials OAuth, independently of normal install/delivery flags. Set the numeric `HUBSPOT_APP_ID` and verify app entitlement in an authorized development account. Run internal `hubspotJournal:configure` once to create/update the app lifecycle subscriptions (`4-1909196` install, `4-1916193` uninstall); it requires `developer.webhooks_journal.subscriptions.write`. The minute reader uses `developer.webhooks_journal.read`. These are developer app grants, not additional account installation scopes. Enable `HUBSPOT_JOURNAL_ENABLED=true` only after validation. No subscriptions or credentials were configured as part of this local code change.

The reader downloads one chronological Journal file per action, processes batches of at most 25 events with a durable per-file position/offset, and continues until caught up. A lease fences concurrent readers; checkpoints and retirement scheduling commit together. It validates app ID, account-level installation scope, action/event type and occurrence time. Account-wide uninstall retires current workspace attachments in bounded pages without another DELETE. Install observations never silently reconnect; authentication failure alone is not uninstall evidence. Delayed events that cannot be correlated with the local installation leave it requiring reconnect and record a diagnostic rather than removing a possibly newer install.

Monitor the `hubspotJournal` singleton's `diagnostic`, `checkedAt`, offset and processing position, plus sanitized action logs. The provider retains only three days of history. Processing/download/auth errors keep the checkpoint, and a detected replay-window gap stops ingestion for operator reconciliation; no automatic skip to latest occurs. After verifying missed account lifecycle events, internal `hubspotJournal:reset` accepts a verified last-processed offset (or `null` to replay the available earliest history) and an evidence reference. It invalidates an older reader claim. Do not reset without reconciling any missing uninstall events. Journal file formats, exact private-app entitlement and offset/no-event behavior require live development verification before activation.

Journal retirement compares the immutable connection `_creationTime` with uninstall time; `installedAt` remains reconnect/cache freshness. A later install observation never exempts a provably older local ID from permanent retirement. A local ID strictly newer than both uninstall and an observed later install is preserved; equality or uncertain chronology suspends credentials for reconciliation. Account-operation confirmation remains conservative about newer remote install evidence and dispatched request reserves, including operations detached by company erasure.

References: [uninstall API](https://developers.hubspot.com/docs/api-reference/latest/app-management/app-uninstalls/uninstall-app), [Journal](https://developers.hubspot.com/docs/api-reference/latest/webhooks-journal/guide), [subscriptions](https://developers.hubspot.com/docs/api-reference/latest/webhooks-journal/subscriptions/guide).

## Delivery, identity and recovery

All saves carry one ordered recoverable command journal with stable interaction IDs and one immutable in-flight batch, whether or not HubSpot is installed. Up to 25 commands are validated sequentially and committed atomically. Intermediate applications are retained even if later replaced or removed. Snapshot reads are shared within the batch; removals emit nothing and need no template reads. The journal is bounded at 250 commands and never compacted by discarding activity. Committed receipts resolve before stale edit conflicts and policy gates, including after another editor’s changes or later installation. Uninstalled companies produce no CRM activity. Empty unchanged saves remain zero-write acknowledgments.

Fresh snapshots without commands are rejected with reload/recovery guidance; retained legacy requests can acknowledge their last accepted operation, conflict against newer state or acknowledge an unchanged no-op. Journal v6 writes commands universally; v4/v5 readers retain old drafts and immutable requests. Ambiguous superseded snapshot outcomes are not reconstructed as activity. Association blocks are distinct from transport failures: drafts remain pending, controlled accepted-request resolution remains possible, and authoritative repair resumes eligible work without clearing unrelated errors. All new approval requests/decisions require operation identities/protocol, and all new exports use stable attempt identities.

`hubspotEvents` is the durable local outbox. Each activity runs independently through a direct Workpool with parallelism five and action retries disabled; only the outbox chooses retries. Enqueue and the event's work/execution identity commit atomically. Completion and recovery match that identity; stale callbacks cannot restart terminal or replacement work. Upload precedes Note creation only within its download. Original `hs_timestamp` determines timeline chronology. Delivery admission starts each minute and continues through native cursor pages of at most 20 rows and 1 MiB per transaction. Each pass keeps its original due-time cutoff across pending, uncertain, working and blocked states, advancing past leased or otherwise skipped rows. Workpool still limits provider execution independently. A five-minute claim plus a 30-second retirement reserve fences abandoned work. Company retirement cancels queued work and waits for started claims; cancellation alone does not stop a running action.

Admission, claim, fresh dispatch and settlement share one evidence policy. Permanently unavailable/replaced undispatched history is `paused`, outside the active sweep. Credential-only `blocked` rows recover through bounded sweeps. A retained dispatch has reconciliation precedence over link repair/pause: it can observe only its original destination. Positive File adoption records the original upload, but cannot authorize a new Note on an unavailable or replaced generation. Ordinary contract deletion preserves accepted history; a missing directory projection falls back to the source contract transactionally.

Claims recheck company/account/credential/link fences before dispatch. Every creation request has a unique persisted dispatch identity. A proven local pre-fetch denial clears only the matching invocation's definitely unsent intent; a provider-returned 429 or a failed reconciliation read never clears an older intent. Unknown post-intent errors remain ambiguous. Current credential generation is checked before storing a generation block or changing shared availability; stale failures cannot install hidden blocks. Current provider 401 observations, including deal browsing without outbox work, use the same fenced Reconnect transition. Other errors do not imply invalid credentials. Positive historical success settles its own row without clearing current unavailability. Contract/company changes never retarget history.

A timeout, lost response or unclassified failure after an attempted write becomes `uncertain`. The worker adopts only positive evidence: matching Note markers in associated Notes, or a deterministic PRIVATE filename plus exact length and SHA-256. A pass covers at most five association pages of 100 Notes, or 100 File candidates. Dispatch-keyed checkpoints retain the current page/candidate IDs, attempted frontier, cursor and bounded unresolved count. A member-local missing/failed read does not suppress later positive members. Completed unresolved passes search again; a partial/absent pass never proves noncreation.

Reconciliation uses bounded **serial** reads, without relying on an unverified Notes batch API. One invocation permits at most 12 HTTP requests, 150 seconds elapsed before its reserve and 64 MiB of candidate body verification. It starts a request only with 30 seconds of segment reserve; a complete File metadata/signing/body unit reserves three requests and 80 seconds. Body reads have a 25-second abort and stream length cap. The five-minute claim leaves additional time for RPC/checkpoint/settlement work. Larger File candidates remain unresolved for operator attention rather than permitting unbounded reads. These are conservative execution bounds, not measured throughput improvements; a complete worst-case serial Note pass still costs up to 505 provider reads.

The automatic horizon is the original dispatch time plus 24 hours. Admission, pauses, yields and failure settlement retain `attention` at that horizon; no retry resets it. Positive results already returned can still settle matching bookkeeping. Exactly-once delivery is not promised. An authenticated direct deal read returning 404 marks only its matching generation unavailable; generic failures, search omissions, 429s and revoked credentials do not imply deletion.

Operators inspect `hubspotEvents` in the intended Convex deployment, using event IDs and sanitized diagnostics. Avoid exposing connection tokens. `hubspotOperations:recover` is internal-only and requires an evidence reference. `disposition: "reconcile"` authorizes one bounded original-dispatch observation segment, including after repair or the automatic horizon. It consumes that authority once without resetting the horizon or permitting a resend. Failed or incomplete work beyond the horizon returns to attention. `"confirmed-not-sent"` clears its dispatch marker only after the operator has established noncreation and recorded evidence. Never use this to guess that an ambiguous Note/File does not exist. Link-generation blocks still apply. No automatic deletion of HubSpot history is performed.

## Downloads and retention

A stable export attempt captures the original destination, title, immutable version, choices and approval generations at reservation. Concurrent preparation is fenced; retries return the adopted bytes. Reservation and release enforce association eligibility; release also rechecks current content and approval state after generation. Relinking does not retarget or rename an attempt that already captured a destination and title. A pre-install reservation with no destination cannot be newly released after installation: its client initiation identity is retired so the next eligible download reserves a fresh attempt. Acknowledgments already journaled after initiation retain their original identity and destination. Preparation alone creates no download activity.

After successful fetch, Blob read and anchor initiation, the browser stores a per-attempt, deployment/member-scoped acknowledgment and asynchronously commits it once. Individual storage keys prevent concurrent tabs overwriting each other's acknowledgments. Recovery snapshots keys before reading/removing them, isolates malformed/terminal entries and persists server-directed future deferral on the original entry and excludes deferred/future-dated entries before its 25-eligible-attempt limit. Terminal too-early timestamps are retired from automatic recovery without changing their original value; account/session/transport failures preserve pending entries. Workspace recovery retries after reload/transport failure independently of optional snapshot caching. Browser initiation cannot prove a disk save; a crash before journaling or unavailable browser storage remains an observation gap.

The application permits local retry only through **reservation time plus one hour**, even after an early upload or Note succeeds. That retry returns the identical adopted blob; it never re-prepares an expired identity. Unlinked acknowledgment adds no attachment hold. An acknowledgment for an active installation with still-eligible retained bytes adds an upload hold through the first server acknowledgment time plus 30 days; replay does not extend it. A confirmed private upload or positive File adoption records remote identity and ends that hold independently of Note completion. Ambiguous uploads retain the bounded hold. Confirmed remote identity can attach even after local bytes are gone.

Retrieval/upload eligibility is distinct from physical cleanup. The attempt remains a storage owner until its last necessary hold plus a **15-minute physical read grace**, then expiry releases the reference and checks competing owners in the same transaction. The five-minute cron starts a fixed-cutoff pass through preparing and ready attempts; native cursor continuations process at most 20 rows and 1 MiB per transaction, advancing past retained attempts without waiting for another cron tick. Confirmation after an older deadline permits a fresh physical grace for an already in-flight bounded provider read, without restoring expired eligibility. This grace covers the sender's bounded retrieval path and ordinary browser transfers; it does not promise arbitrary-duration browser reads or immediate physical deletion at the eligibility deadline. No supported atomic storage-read/delete guarantee is assumed. The independent 24-hour orphan sweep recognizes attempt ownership.

Complete immutable provenance remains until company deletion: ordered item/concession IDs, optional original review application IDs/statuses, template/edit/review generations, actor/title/destination, attempt/release/acknowledgment facts, filename/hash/size and remote identity. Selection chunks use one compact ordered tuple representation for preparation and permanent identity; no redundant verbose selection is written. Receipt chunks are separate and retained. A valid late acknowledgment preserves initiation facts. While its installation remains active, it also records one truthful event with missing attachment when neither eligible bytes nor verified remote identity exists; removed installations create no new event or upload hold.

Ordinary contract deletion retains accepted company history. Company deletion removes credentials first, cancels queued Workpool work, waits for bounded started actions, and retires events, attempts, file holds, generation blocks, receipts, chunks and OAuth states through bounded phases. Previously written HubSpot records are retained.
